# 为什么需要 K8s — 核心概念

先回答"为什么"，再碰命令。本章不装任何东西，只建立正确的思维模型——这决定了后面学 K8s 是"越学越顺"还是"越背越晕"。

## 1. Docker Compose 管不了的事

你在 Docker 课程里用 Compose 一条命令拉起三个容器——单机上很美好。现在换成生产：

| 现实问题 | Compose 的窘境 | K8s 的答案 |
|----------|----------------|------------|
| 容器挂了谁来重启？ | 没有（要自己写脚本） | 自动重启、自动重建（自愈） |
| 流量怎么分到多个副本？ | 手动映射端口 | Service 统一入口 + 负载均衡 |
| 发布新版本怎么不中断？ | down 再 up，有中断窗口 | 滚动更新，逐个替换 |
| 机器挂了容器去哪？ | 跟着没了 | 调度器把容器搬到健康节点 |
| 20 台机器谁管理？ | 每台手装 Compose | 集群统一调度 |

**一句话定位**：Docker 是"集装箱"，K8s 是"自动化港口"——调度、装卸、监控、消防全自动化。

## 2. 集群架构：控制面与工作节点

```
┌─────────────── 控制面（大脑）───────────────┐
│ API Server（唯一入口，kubectl 连它）          │
│ etcd（集群的全部状态数据库）                  │
│ Scheduler（决定容器放哪台机器）               │
│ Controller Manager（让现实匹配期望）          │
└──────────────────┬─────────────────────────┘
        ┌──────────┼──────────┐
   ┌────▼───┐ ┌────▼───┐ ┌────▼───┐
   │ 节点 1  │ │ 节点 2  │ │ 节点 3  │   ← 工作节点（干活的机器）
   │ kubelet │ │ kubelet │ │ kubelet │   ← 每台一个"工头"
   │ 容器们  │ │ 容器们  │ │ 容器们  │
   └─────────┘ └─────────┘ └─────────┘
```

记忆法：**控制面 = 大脑（决策），节点 = 肌肉（跑容器），kubelet = 每台肌肉上的神经**。学习阶段用 minikube 把两者装进一台机器，概念不变。

## 3. 三个最重要的对象

K8s 的一切皆"对象"（资源）。先掌握这三个，其余用到再查：

| 对象 | 一句话 | 类比 |
|------|--------|------|
| **Pod** | 最小部署单元 = 1 个或几个共生容器 | 合租屋（同 IP 同存储，同生共死）|
| **Deployment** | 管 Pod 的副本数和版本 | 物业（保证 3 间房都在、想换家具逐间换）|
| **Service** | 一组 Pod 的稳定访问地址 | 前台总机（Pod 换了号码，总机号不变）|

**为什么要 Deployment 管 Pod**：Pod 挂了不会自己复活；Deployment 的职责就是"我声明要 3 个副本，少了就补"。这引出 K8s 的灵魂——

## 4. 声明式思维（本课程最重要的一节）

```yaml
# 你不命令 K8s "去启动 3 个容器"（命令式）
# 而是声明 "我的期望状态是 3 个副本"（声明式）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web          # 这个 Deployment 叫 web
spec:
  replicas: 3        # 期望：3 个副本
```

提交后，Controller 持续对比"现实"和"期望"：Pod 挂了（现实=2）→ 自动补到 3。发布新版本 = 修改期望（镜像 v2）→ 逐个替换。**你永远只说"我要什么"，不说"怎么做"。**

对比 Ansible（阶段6 学的也是声明式思想）你会发现基础设施领域的共同趋势——这套思维比任何命令都值钱。

## 常见误区

1. **把 Pod 当虚拟机用** —— Pod 是易逝的（随时可能被重建/迁移），别在里面存数据（数据放卷/数据库）、别依赖固定 IP（访问走 Service）
2. **一上来背 30 个对象** —— 深挖 Pod/Deployment/Service 三件套，其余（Ingress、ConfigMap…）遇到需求再学，效率高十倍
3. **用命令式思维理解 K8s** —— "我删了 Pod 它怎么又回来了？！"——因为你删的是现实，Deployment 的期望还在；改期望才是正道

## 小结

- K8s = 自动化港口：自愈、调度、滚动发布、负载均衡
- 架构 = 控制面（大脑）+ 节点（肌肉）+ kubelet（神经）
- 三件套：Pod（合租屋）→ Deployment（物业）→ Service（总机）
- 灵魂是声明式：只说"要什么"，控制器负责"达成"

## 练习

1. 用自己的话（不用术语）向朋友解释"为什么 Compose 不够用"
2. 画出"用户请求 → Service → Pod"的访问路径草图
3. 思考：把 `replicas: 3` 改成 `replicas: 5`，谁去真正启动了那 2 个新 Pod？
