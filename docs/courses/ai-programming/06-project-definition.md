# 项目选题与定义

"做了个 Todo List"和"做了个能跑的生产级小系统"，在面试官眼里是两个人。本章解决 AI 编程的临门一脚：**选一个值得做的项目，把它定义清楚**——定义的质量直接决定项目的上限。

## 1. 面试官眼里的好项目

| 维度 | ❌ 减分项 | ✅ 加分项 |
|------|-----------|-----------|
| 选题 | 教程复刻、Todo/博客第 N 次 | 真实痛点、自己真是用户 |
| 规模 | 半天糊完 or 永远做不完 | 2-6 周出 MVP，有迭代痕迹 |
| 完成度 | 能跑就行 | 测试、文档、备份、错误处理齐全 |
| 深度 | 堆功能 | 有 2-3 个"为什么这么设计"能讲 |
| 证据 | 只有口头描述 | git 历史 + 可 clone 一键跑 |

**核心认知**：面试官不看项目多大，看**工程判断力**——你在约束下做了哪些取舍、为什么。AI 时代尤其如此：功能谁都能"生成"出来，判断力生成不了。

## 2. 选题三原则

1. **自己是第一个用户**：解决你自己的真实麻烦（每天遇到的、会向朋友吐槽的）。真实的痛让需求定义自然清晰，也让面试故事有血肉
2. **与目标岗位对齐**：想投运维就做运维工具，想投后端就做有 API 和数据层的东西——把目标 JD 里的关键词圈出来，项目覆盖其中 3-5 个
3. **两周能出 MVP**：宁可小而完整，不要大而烂尾。完成一个项目学到的东西 + 面试价值，远超开三个坑

## 3. 五大项目原型（IT 方向求职友好）

| 原型 | 示例 | 展示的岗位能力 |
|------|------|----------------|
| **知识库/文档站** | 团队运维手册站（就是本项目 it-infra-trainer 这种） | 信息架构、文档能力、前端基础 |
| **巡检/报告自动化** | 定时巡检服务器，AI 汇总生成中文日报 | 脚本、定时任务、AI 集成 |
| **日志分析助手** | 贴日志→AI 定位异常模式→给出排查建议 | 日志体系、提示词工程 |
| **小工具+CLI** | 密码强度审计器、证书到期监控 | 单一功能做透、工程完成度 |
| **迷你平台** | 书签管理、订阅追踪（带用户系统） | 前后端+数据库全链路 |

> 原型只解决"不知道做什么"。决定性的是**往里注入你自己的场景**：同一个巡检工具，巡检你的 NAS 和巡检"公司 200 台服务器"（编的）完全两回事——面试官一问细节就露馅。

## 4. 需求文档：一张纸模板

```markdown
# 项目需求定义：XXX

## 1. 一句话定位
给 [谁] 解决 [什么问题]，替代他们现在的 [什么做法]。

## 2. 背景（3-5 行）
我为什么做：[真实场景 + 现有方案的痛]

## 3. 功能需求（MoSCoW）
Must   核心闭环，MVP 必须：A、B、C
Should  重要的第二梯队：D
Could  有时间再说：E
Won't  明确不做（非目标）：Web 界面、多用户、云同步

## 4. 成功标准（可验证）
- [ ] 一条命令完成核心操作，出错有明确提示
- [ ] npm test 全绿（语法+冒烟+构建）
- [ ] 新用户按 README 十分钟内跑起来

## 5. 技术约束
栈：[Node/Python + X]；运行环境：[本地/WSL]；
外部依赖：[无 / 某免费 API]；数据：本地文件或 SQLite

## 6. 里程碑
M1（第1周）：核心闭环 A+B 可用
M2（第2周）：C + 测试 + README
M3（可选）：D + 部署演示
```

**最值钱的仍然是"非目标"**：AI 最容易把项目做膨胀，Won't 列表是你的挡箭牌。**成功标准必须可验证**——"做个好用的工具"不是标准，"十分钟跑起来+全绿"才是。

## 5. 用 AI 帮你定义项目（而非替你定义）

正确用法——AI 当"需求评审员"：

```text
"这是我的需求文档（贴上）。请扮演挑剔的技术评审：
 1. 哪些需求模糊到无法验收？
 2. Must 是否构成最小闭环？多了还是少了？
 3. 有哪些我没写但面试官一定会问的边界情况？
 只提问，不要替我改需求。"
```

一轮评审通常能挖出 5-8 个漏洞。**决定权留在你手里**——需求是项目的灵魂，外包灵魂的项目答辩必挂。

## 常见误区

1. **选题追热点**（"做个 AI 大模型应用"）—— 评估能力为零的空壳；热点放进"怎么实现"里，别放在"做什么"里
2. **需求文档写给 AI 看**—— 文档首先是给你自己和面试官看的；自己都讲不清的需求，AI 只会陪你一起糊涂
3. **MVP 里塞 Should/Could** —— 膨胀是烂尾之母；MVP 上线后再迭代，git 历史里"迭代痕迹"本身就是面试素材

## 小结

- 好项目 = 真实痛点 + 岗位对齐 + 两周 MVP + 工程完成度
- 一张纸需求：MoSCoW + 非目标 + 可验证成功标准 + 里程碑
- AI 当评审员不当决策者；决定权外放 = 答辩必挂

## 练习

1. 按三原则选出你的项目，写出一句话定位和 3 条 Must
2. 完成整张需求文档，跑一轮"AI 挑剔评审"，人工修订
3. 给里程碑 M1 定一个"完成日"，写进日历
