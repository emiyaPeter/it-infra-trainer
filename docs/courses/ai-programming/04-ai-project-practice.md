# 带着 AI 做完整项目

前三章是"招式"，本章是"实战"：用一个真实小项目走完 需求 → 设计 → 实现 → 测试 → 交付 全流程，并沉淀一份踩坑清单。

## 预备课：环境搭建一步一命令

::: info 零基础同学照抄即可（每行输完按回车）
```bash
# 1. 安装 Node.js：去 https://nodejs.org 下载 LTS 版本，
#    双击安装（一路下一步）。装完打开新终端验证：
node -v          # 显示 v20.x.x 或更高就成功了

# 2. 建项目文件夹并进入
mkdir bm         # bm = bookmark 项目名，可自定
cd bm

# 3. 初始化 git（时间机器）和 npm（包管理）
git init         # 若提示"git 不是命令"：去 https://git-scm.com 安装
npm init -y      # 生成 package.json（项目的身份证）

# 4. 验证：能看到 .git 文件夹和 package.json 文件
ls               # Windows 用 dir
```
四步做完，你的"厨房"就备好了。之后所有代码都写在 `bm` 文件夹里。
:::

## 1. 实战项目：个人书签管理器（纯本地）

选它的原因：规模适中（3-5 文件）、技术栈熟悉（Node.js + SQLite，前几阶段都学过）、有真实功能闭环。

### 第一步：需求定义（人主导）

```text
【需求】本地书签管理 CLI
- 添加书签：bm add <URL> [标签...]，自动抓取页面标题
- 列表：bm list [--tag xxx]，表格输出，支持按标签过滤
- 删除：bm rm <id>
- 数据存 SQLite（bookmarks 表），文件在 ~/.bm.db
【非目标】不做 Web 界面、不做多用户、不做云同步（明确排除防 AI 过度设计）
```

**"非目标"是需求文档里最值钱的一节**——AI 最擅长"顺手"做出一堆你没要的东西。

### 第二步：让 AI 出设计并压缩

```text
"基于以上需求给出设计：表结构、文件划分、每个命令的处理流程。
 不写代码。设计要最小化——能一个文件解决的不要拆五个。"
```

拿到方案后人工砍：AI 首版设计常有过度分层（controller/service/repository 三层对 200 行代码是灾难）。**小项目就该"一个 db.js + 一个 cli.js"**。

### 第三步：逐命令实现 + 即时验证

节奏：`add` 命令 → 手工测 → commit → `list` → 测 → commit → `rm` → 测 → commit。每个命令实现前重申一句"只实现 X，不动其他"。

### 第四步：收尾三件事

1. 让 AI 写 README（用法示例必须它自己验证过能跑）
2. 加自检脚本（哪怕只是 `node --check` 所有文件）
3. 让 AI 假装"第一次见这个项目"的用户，通读代码找问题——角色转换后的审查常能发现新问题

## 2. 踩坑清单（每一坑都真实常见）

| 坑 | 现象 | 预防 |
|----|------|------|
| **幻觉 API** | 用了不存在的库方法，报错它还"修复"三次都不对 | 关键 API 让它引用官方文档；换你自己熟的库 |
| **过度工程** | 200 行的项目给出三层架构+依赖注入 | 需求里写明"非目标"；设计阶段人工压缩 |
| **自作主张** | 只让改 A，它顺手把 B C D 也"优化"了 | 边界约束 + diff 审查 + 一个任务一个 commit |
| **上下文漂移** | 长会话后忘记约定，风格前后不一 | 逻辑单元完成即提交+新会话；约定写进 AGENTS.md |
| **测试敷衍** | 生成的测试只测 happy path | 明确要求覆盖错误分支；测例本身也要 review |
| **静默降级** | 功能做不出来就偷偷简化需求不告诉你 | 要求"任何偏离需求的改动必须先说明" |

## 3. 代码审查要点（AI 产物的专属清单）

- **正确性**：API 名逐个核对；边界条件（空输入、超长、并发）谁处理了
- **错误处理**：是 `try/catch` 后吞掉，还是有意义的提示？
- **安全**（第五章展开）：路径拼接、命令执行、SQL 拼接
- **依赖**：新引入的包是否必要？维护状态如何？
- **一致性**：命名、缩进、错误风格是否和项目现有代码一致

> 经验值：**AI 写得越"顺滑漂亮"的代码越要细看**——样板式的完美代码里最容易混入一个幻觉 API。

## 4. 什么时候应该放弃 AI 自己写？

诚实的成本收益判断：

- 需求你自己都说不清 → 先想清楚再找 AI（提示词救不了糊涂需求）
- 涉及冷门库/内部私有 SDK → 文档比 AI 准
- 改动核心且无测试保护 → 先补测试护栏再让 AI 动手
- 十几行的改动 → 自己写比写提示词快

## 常见误区

1. **把"做完"当"做对"** ——能跑 ≠ 边界处理了 ≠ 无安全问题，验证标准要提前定
2. **跳过设计直接堆功能** ——返工时最贵的不是代码是已写代码背后的"错误地基"
3. **一次会话从头做到尾** ——上下文漂移是必然，切会话不是麻烦是纪律

## 小结

- 流程：需求（含非目标）→ 设计（人工压缩）→ 逐件实现验证 → 收尾三件事
- 六大坑：幻觉 API、过度工程、自作主张、上下文漂移、测试敷衍、静默降级
- 越漂亮的 AI 代码越要细看；算清成本，有些活自己写更快

## 练习（本章是实操章）

1. 把书签管理器（或你自己的等价小项目）按全流程做出来
2. 在过程中记录你遇到的坑，归入踩坑清单对照
3. 用"用户角色扮演"法让 AI 审查自己的产出，统计找到的问题数
