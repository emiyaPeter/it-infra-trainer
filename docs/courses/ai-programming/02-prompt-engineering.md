# 提示词工程实战

提示词（Prompt）就是给 AI 的"需求文档"。给新人的需求文档写得烂，产出就烂；给 AI 同理。本章是一套可直接套用的提示方法。

## 1. 结构化提示四要素

差提示 vs 好提示，差的就是结构：

```text
❌ 差："帮我写个备份脚本"

✅ 好：
【背景】我在 Ubuntu 上运行一个个人网站，代码在 /var/www/myapp，
       想每天凌晨 2 点备份到 /backup，磁盘只有 20G 空闲。
【任务】写一个 bash 备份脚本 + 对应的 systemd timer 配置。
【约束】
  - 用 tar.gz，保留最近 14 天，旧的自动删除
  - 备份完成后校验 sha256
  - 失败时在日志里输出明确原因
【示例】不需要示例，按以上要求直接给出两个文件的完整内容。
```

四要素速记：**背景（Context）→ 任务（Task）→ 约束（Constraints）→ 输出格式（Format）**。其中**约束最常被漏掉**——不留约束，AI 会按"通用最佳实践"自由发挥，而通用往往不是你要的。

## 2. 迭代式对话：像带实习生一样反馈

第一版输出不满意很正常，关键是**给出具体反馈**而不是"不对，重写"：

```text
❌ "不对，再改改"            → AI 只能瞎猜哪里不对

✅ "三点反馈：
   1. 保留策略改成保留 14 份（按份数不按天数）
   2. tar 前先停写：加 flock 锁
   3. 日志加时间戳前缀"
```

**节奏心法**：一次只推进一小步（先要方案 → 认可后再要代码 → 再要测试），不要一句"把整个系统写出来"。步子越小，纠偏成本越低。

## 3. 计划先行：让它先说思路再动手

对任何超过一个文件的任务，先要计划：

```text
"先不要写代码。请给出：
 1. 你打算分几步实现
 2. 每步会改动哪些文件
 3. 有什么风险
我确认后你再开始写。"
```

好处：计划阶段的错误改一句话，代码阶段的错误改一百行。这也是后续章节"终端代理工作流"的核心思想。

## 4. 约束边界：保护你的代码库

让 AI 改代码时，**明确圈定活动范围**：

```text
"只修改 src/auth.js 中的 login 函数。
 不要动其他文件。
 不要改变函数签名。
 不要引入新依赖。
 保持现有代码风格（4 空格缩进、单引号）。"
```

没有边界的"顺手优化"是 AI 改码最大的坑之一——它会把整个文件重排格式、升级语法、改你没让它动的逻辑。

## 5. 高级技巧三则

- **少样本示例（Few-shot）**：给出 1-2 个"输入→期望输出"的例子，比千言万语的描述都准——尤其适合格式转换、日志解析类任务
- **要求复述任务**：长需求末尾加一句"开始前先用三点复述你对需求的理解"——暴露理解偏差的廉价手段
- **要求自检**：输出后追加"检查你的答案：是否有不存在的方法？是否满足全部约束？逐条列出核对结果"——能打掉相当一部分低级幻觉

## 常见误区

1. **一句话需求 + 期望完美产出** —— 省下的提示时间会加倍花在返工上
2. **把全部背景一股脑贴进去** —— 无关信息冲淡重点；只给与任务相关的上下文
3. **任务失败就换话题重来** —— 先诊断：是需求没说清？约束没给？还是触发了幻觉？对症下药比换姿势有用

## 小结

- 四要素：背景、任务、约束、格式——约束是灵魂
- 小步迭代 + 具体反馈；大任务先要计划
- 改代码必须圈边界；示例、复述、自检是三个廉价增强

## 练习

1. 用四要素结构重写你最近一次失败的 AI 提问，对比产出质量
2. 让 AI 给你的项目加一个功能：先要计划，人工审查计划后再放行，记录这样避开了什么坑
3. 故意不加"不要引入新依赖"的约束，看它会不会拉进三个新包
