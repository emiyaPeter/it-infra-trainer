# 安全基础概念

安全不是一款产品，而是一种思维方式。在学任何具体的"安全技术"之前，必须先建立安全思维框架。

## CIA 三元组：安全的三个维度

CIA 是信息安全最核心的模型，所有安全措施都在保护这三个属性：

```
      机密性 (Confidentiality)
      ／          ＼
     ／            ＼
    ／    CIA       ＼
   ／   三元组        ＼
  完整性 ──────────── 可用性
(Integrity)          (Availability)
```

### 机密性 (Confidentiality)

**数据只能被授权的人访问。**

| 威胁 | 防护措施 |
|------|---------|
| 数据泄露 | 加密（传输 + 存储）|
| 未授权访问 | 访问控制、认证 |
| 窃听 | TLS/SSL、VPN |
| 内部泄密 | DLP（数据防泄漏）|

**实战场景**：
- 数据库中的密码 → 用 bcrypt 哈希，不存明文
- 用户数据在网络上传输 → 强制 HTTPS
- 离职员工 → 立即吊销所有账号和访问权限

### 完整性 (Integrity)

**数据没有被未授权地修改或破坏。**

| 威胁 | 防护措施 |
|------|---------|
| 数据篡改 | 数字签名、哈希校验 |
| MITM 中间人攻击 | TLS 证书验证 |
| 日志被删 | 写入专用日志服务器 |
| 软件被植入后门 | 代码签名、完整性校验 |

**实战场景**：
- 下载 ISO 镜像后 → 校验 SHA256 是否与官方一致
- Web 应用 → 使用 HTTPS 防中间人篡改
- 关键文件 → 用 `aide` 或 `tripwire` 监控文件完整性变化

### 可用性 (Availability)

**授权用户需要时，系统和数据可以正常访问。**

| 威胁 | 防护措施 |
|------|---------|
| DDoS 攻击 | CDN、流量清洗、弹性扩容 |
| 硬件故障 | 冗余、RAID、热备 |
| 勒索软件 | 离线备份、3-2-1规则 |
| 自然灾害 | 异地灾备 |

**实战场景**：
- 服务器单点故障 → 加负载均衡 + 多节点
- 数据库 → 主从复制 + 自动故障转移
- 备份 → 3份副本、2种介质、1份异地

## 纵深防御 (Defense in Depth)

**单层防御一定会被突破。安全应该像洋葱——一层又一层。**

```
      ┌─────────────────────────┐
      │    物理安全              │  ← 门禁、监控、机柜锁
      │  ┌───────────────────┐  │
      │  │   网络安全          │  │  ← 防火墙、IDS/IPS、NAC
      │  │  ┌─────────────┐  │  │
      │  │  │ 主机安全      │  │  │  ← 防病毒、HIDS、补丁管理
      │  │  │  ┌───────┐  │  │  │
      │  │  │  │应用安全 │  │  │  │  ← WAF、输入验证、认证
      │  │  │  │┌─────┐│  │  │  │
      │  │  │  ││数据  ││  │  │  │  ← 加密、访问控制、审计
      │  │  │  │└─────┘│  │  │  │
      │  │  │  └───────┘  │  │  │
      │  │  └─────────────┘  │  │
      │  └───────────────────┘  │
      └─────────────────────────┘
```

**举例：保护一个 Web 应用**：
1. 物理层：服务器在锁着的机房里
2. 网络层：防火墙只开放 80/443；DDoS 防护
3. 主机层：系统已加固、补丁最新、只装必要的软件
4. 应用层：WAF 过滤 SQL 注入/XSS；输入验证
5. 数据层：数据库加密；日志记录所有访问

## 最小权限原则 (Least Privilege)

**只给完成任务所需的最小权限——不多不少。**

```
❌ 错误做法:                       ✅ 正确做法:
开发者有 root 权限                 开发者只能访问开发环境
实习生能看到所有客户数据            实习生能看到脱敏的数据
所有服务用同一个账号                每个服务有独立的最小权限账号
```

**实战案例**：
- Linux：用 `sudo` 而不是直接 `root`，控制谁能 sudo
- 数据库：应用账号只有 CRUD 权限，没有 DDL（不能删表）
- 云上 (AWS IAM)：EC2 只读就不能删 S3；时间限制 + MFA

## 零信任 (Zero Trust)

**"从不信任，始终验证"** —— 不管你在内网还是外网，每次访问都要验证。

| 传统模型 | 零信任模型 |
|---------|-----------|
| 内网 = 可信 | 内外网都不可信 |
| VPN 接入后畅通无阻 | 每次请求都验证 |
| 静态权限 | 动态权限 + 持续评估 |
| 边界防护为主 | 身份防护为主 |

**零信任三大支柱**：
1. **验证用户** (MFA, SSO)
2. **验证设备** (是否合规？是否中毒？)
3. **限制访问** (微隔离，最小权限)

## 风险评估：安全决策的基础

安全不是绝对的——你需要权衡**风险 vs 成本**。

```
风险 = 威胁 × 脆弱性 × 资产价值
```

**评估流程**：
1. 识别资产（这个数据/系统有多重要？）
2. 识别威胁（谁会攻击？为什么？）
3. 识别脆弱性（有什么漏洞可以被利用？）
4. 评估影响（被攻破后损失多大？）
5. 决策（接受风险？缓解？转移？避免？）

**实战举例**：
> 一个内部 Wiki 系统，没有敏感数据
> - 花 10 万买 WAF 保护它 → ❌ 过度防护
> - 只做基本的访问控制和备份 → ✅ 合理的风险接受

> 核心交易数据库，包含用户信用卡信息
> - 加密 + 审计 + HIDS + 备份 + WAF + 渗透测试 → ✅ 值得投入

## 动手练习

1. 分析你的个人电脑/web 应用：它在 CIA 三方面各有什么风险？
2. 查看你的 Linux 系统：哪些账号是 root？哪些服务在用特权运行？
   ```bash
   # 查看 sudo 配置
   sudo cat /etc/sudoers
   # 查看以 root 运行的进程
   ps aux | grep root | head -20
   ```
3. 思考：如果你负责一个电商网站的安全，你会从哪些层面防护？
