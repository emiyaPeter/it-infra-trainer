# 灾备规划与演练

前几章有了"零件"（备份、冗余、LB/转移），本章把它们组装成**制度**：分级灾备方案、恢复手册、演练机制。灾难之夜，救你的不是技术，是**演练过的流程**。

## 1. 灾备等级与成本曲线

| 等级 | 模式 | RTO | RPO | 成本 | 适合 |
|------|------|-----|-----|------|------|
| 冷备 | 设备到位、数据备份异地，出事再装系统 | 天级 | 小时级 | 💰 | 边缘业务 |
| 热备 | 备机房常备运行环境，数据准实时同步，**出事才切** | 分钟级 | 分钟级 | 💰💰💰 | 核心业务主流 |
| 双活 | 两地同时服务、流量分担，**无感切换** | 秒级 | 秒级 | 💰💰💰💰💰 | 支付、交易 |

**决策逻辑**：业务每停 1 小时损失多少（钱/声誉/合规）？对照各等级成本，选"损失 ≥ 成本"的最低档。不是所有系统都值得双活——**分级**是灾备规划的第一动作。

## 2. 异地数据同步方式

```text
存储层复制：SAN/分布式存储跨机房镜像 —— 块级，通用但"盲"（连带误操作一起复制）
数据库复制：MySQL 主从 / PG 流复制 —— 结构化，可延迟、可审计
应用层双写：写两套 —— 最灵活也最容易错，慎用
备份异步搬运：rsync / 对象存储跨区复制 —— 最朴素，RPO 最差但最抗误删
```

::: tip 误删防护组合拳
同步复制会把你"删库"操作忠实同步过去——所以热备之外，**必须**叠加"快照+版本化备份"（第一章的不可变存储）。同步防机房级故障，备份防逻辑级错误，二者防的不是同一种灾难。
:::

## 3. 恢复手册（Runbook）——纸上的救命稻草

模板（每个核心系统一份，打印版放得离机房足够远）：

```markdown
## 系统名：订单数据库 故障恢复手册 v2.3
责任人：张三（主）/ 李四（备）   电话：...
依赖：机房A机柜12 / MySQL 8 主从 / 监控: Prometheus

### 场景1：主库硬件故障（预期 RTO 15min）
1. 确认从库同步状态: SHOW SLAVE STATUS\G  （Seconds_Behind_Master < 10）
2. 应用侧切换只读→提升从库为主（执行 promote.sh，路径:...）
3. 改 DNS/虚拟IP指向新主（命令:...）
4. 通知业务方验证下单流程
5. 事后：新起从库补齐，复盘

### 场景2：误删表（预期 RPO 5min，依赖 PITR）
1. 停止对该库写入（应用开关:...）
2. binlog 定位误删 GTID: ...
3. 从最近全量+binlog 恢复到删除前: restore.sh --gtid=...
...
```

写手册的检验标准：**半夜被叫醒、没有电脑查资料**的情况下，按纸面步骤能走通。命令要写全路径，联系人要有备份人选。

## 4. 演练：把纸面变成肌肉记忆

| 类型 | 频率 | 做法 |
|------|------|------|
| 备份抽检恢复 | 每月 | 随机抽一份备份恢复到隔离环境并校验 |
| 单机故障切换 | 每季度 | 关一台生产节点，观察自动转移是否达标 |
| 机房级演练 | 每年 | （或有条件时）模拟整机房失联，按手册切灾备 |
| 红蓝对抗式 | 不定期 | "突击"：不预告，直接注入故障 |

**演练记录模板**：日期 / 场景 / 计划 RTO·RPO / 实测 RTO·RPO / 失败点 / 改进行动项（带责任人和期限）。实测超标的，就是下次改进清单——**演练不是为了通过，是为了暴露问题**。

## 5. 一张自检清单（贴在工位）

- [ ] 每个核心系统都有明确的 RPO/RTO 数字并经业务确认
- [ ] 备份遵循 3-2-1，且至少一份不可变/离线
- [ ] 上月抽检过备份，恢复成功且留档
- [ ] 每份手册在 6 个月内被演练过一次
- [ ] 联系人清单有效（测试过电话）
- [ ] 演练发现问题全部闭环或有跟踪
- [ ] 灾备系统自身的监控和告警正常（别让备份机悄悄死了半年）

## 常见误区

1. **"买了双活就万事大吉"**——从不演练的双活，切换当天大概率失败（依赖漂移、数据不一致、防火墙规则没同步）
2. **手册躺在 Wiki 里没打印**——恰好在断网断电时打不开
3. **演练永远"成功"**——预设剧本、提前打招呼的演练查不出真问题；要逐步加入"突袭"和"连环故障"
4. **只演练技术不演练人**——谁有权拍板切换？决策链演练同样重要

## 小结

- 分级（冷/热/双活）+ 按业务损失选档
- 同步防机房故障、备份+不可变防逻辑错误，缺一不可
- Runbook 要"半夜裸考可用"；演练要留实测数据并闭环问题

## 练习（阶段10 结业）

1. 为你实验环境里的 myapp 写一份完整恢复手册（含两种场景）
2. 组织一次"个人演练"：随机挑最近一次备份，掐表恢复，记录实测 RTO
3. 终期项目预热：设计一套"两台虚拟机 + Nginx + Keepalived + 每日备份"的小型高可用方案，画出架构图并列出你的 RPO/RTO
